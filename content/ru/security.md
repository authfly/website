# Модель безопасности

Authfly держит Stalwart как приватный бэкенд. Из интернета видны Authfly и почтовые порты, больше ничего.

## Что откуда доступно

| Поверхность | Где | Зачем |
|---|---|---|
| Authfly `:4000` (или 443) | публично | готовые страницы, JSON API, проксируемые OIDC-эндпоинты |
| SMTP 25, submissions 465, IMAPS 993 | публично, если нужна почта | почта; обычного IMAP-листенера нет |
| HTTP Stalwart `:8080` (управление, JMAP, `/api/*`) | `127.0.0.1` и внутренняя сеть | управление никогда не должно быть публичным |
| Authfly Console `:4500` | `127.0.0.1` | приватный конфигуратор, доступ через SSH-туннель |
| admin API Authfly `:4001` | только внутренняя сеть, не публикуется | используется Console |

## OIDC через белый список

Stalwart отдаёт OIDC, управление JMAP, `/api/*`, device flow, динамическую регистрацию клиентов и introspection на одном листенере. Публикация его, даже с фильтром путей в обычном прокси, открывает всё это. Authfly публикует только discovery (переписанный), JWKS, token и userinfo; любой другой путь отвечает 404 или 405. См. [HTTP API](/ru/reference/http-api#oidc-эндпоинты).

## Закрытие шагом stalwart-init

До старта Authfly одноразовый шаг `stalwart-init` (идемпотентный) выполняется с bootstrap-админом:

1. проверяет, что почтовый домен существует;
2. создаёт роль с минимальными правами `authfly-service` (роль User плюс управление аккаунтами, чтение доменов, impersonation и чтение блобов для GDPR-выгрузки, обслуживание хранилища для очистки после удаления);
3. создаёт сервисный аккаунт `authfly-svc@<domain>` с этой ролью; Authfly работает от него, никогда от админа;
4. выключает веб-админку и приложение аккаунта Stalwart;
5. выключает client metadata documents и регистрирует клиентов (`app.clients` и сам Authfly).

## Сессии и защита от злоупотреблений

- Публичная регистрация по умолчанию выключена; нужен инвайт.
- Встроенные зарезервированные имена (`admin`, `postmaster`, `abuse`, `root`, …) занять нельзя; список расширяется через `AUTHFLY_RESERVED_NAMES_FILE`.
- Адрес клиента берётся из `X-Forwarded-For` только для запросов от `AUTHFLY_TRUSTED_PROXIES`.
- Пакеты политик не пускают IP-адреса в журнал Authfly; `doctor` это проверяет.

## Console

Console — админ-интерфейс для GDPR-действий и состояния Authfly: подписанная cookie сессии (8 ч), блокировка после пяти неудачных входов, CSRF-токены, CSP без inline-скриптов, журнал с хеш-цепочкой, ввод подтверждения перед разрушительными действиями. Открывайте её только через SSH-туннель:

```sh
ssh -N -L 4500:127.0.0.1:4500 you@203.0.113.10
```

## Канал релизов

Релизам доверяют только через подписанный канал: SSHSIG поверх `channel.json` аппаратным FIDO2-ключом, доверенные ключи встроены в CLI, бинарники закреплены по sha256, образы — по digest. См. [Концепции](/ru/concepts#подписанный-канал-релизов).

## Чек-лист для продакшена

- `public_url` — `https://`; cookies тогда `Secure`.
- Порты 8080, 4500 и 4001 недоступны снаружи; `/jmap`, `/api/*` и `/admin/` отвечают 404/405 на публичном хосте.
- `authfly secrets` показывает все секреты с правами 0600; ни одного секрета в git, argv или истории shell.
- `authfly doctor` проходит (ожидаемый FAIL — только при сознательной подмене образа).
- Бэкап хотя бы раз восстановлен на запасном хосте.
- DNS почты (SPF, DKIM, DMARC, PTR) настроен до того, как вы полагаетесь на письма на другие домены.

## Сообщить об уязвимости

Сообщайте приватно через GitHub security advisories в соответствующем репозитории организации authfly, а не в публичном issue.

> **Не проверено:** приватные сообщения об уязвимостях включаются для каждого репозитория отдельно; проверьте вкладку Security репозитория.
